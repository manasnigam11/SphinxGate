What is an upstream API?

    Examples in our project:
        - Gemini
        - Groq
        - Open-Meteo
        - JokeAPI
        - Frankfurter

From our application's perspective:

    Our Application
          ↓

          ↓
    Upstream Provider


2. THE ACTUAL PROBLEM
──────────────────────────────────────────────────────────────────────────────
She needs to understand that the problem isn't simply:

    "An API sometimes gives an error."

The real problem is:

    When an application depends directly on an external API, an upstream failure
    can propagate into the application and ultimately affect the user.

Example:

    Customer
       ↓
    Logistics Application
       ↓
    External API
       ↓
    API outage
       ↓
    Application request fails
       ↓
    Customer affected


3. WHY IS THIS IMPORTANT?
──────────────────────────────────────────────────────────────────────────────
She should know these consequences:

    Availability
        The application may become unavailable for functionality dependent
        on that API.

    Latency
        A slow upstream API makes the application's response slow.

    Rate limits
        Too many requests can cause: 429 Too Many Requests

    Cascading failures
        Repeatedly calling an unhealthy API can make the situation worse.

    Dependency risk
        The application becomes heavily dependent on one external service.


4. WHO IS AFFECTED?
──────────────────────────────────────────────────────────────────────────────
She should be able to answer this clearly.

    Directly — Application developers / engineering teams
        They have to deal with:
            - provider failures
            - retries
            - timeouts
            - API keys
            - rate limits
            - provider-specific errors

    Indirectly — End users
        They experience:
            - slow responses
            - errors
            - unavailable functionality

    Organizations can experience:
        - service disruption
        - operational overhead
        - dependency on a single provider
        - increased cost during failures


5. WHY NORMAL / DIRECT INTEGRATION FALLS SHORT
──────────────────────────────────────────────────────────────────────────────
Suppose: Application → Gemini

If Gemini fails:  Application → ❌

Developers then have to individually implement:
    - retry
    - timeout
    - fallback
    - rate limiting
    - circuit breaker
    - logging

    ... for every external dependency. That becomes duplicated and difficult
    to maintain.

SphinxGate changes this to:

    Application
         ↓
     SphinxGate
         ↓
    External APIs

    The resilience logic is centralized.


6. WHAT SAANVI SHOULD SAY ABOUT SPHINXGATE
──────────────────────────────────────────────────────────────────────────────
Her basic explanation:

    "SphinxGate is designed as a reliability layer between an application and
    its external API dependencies. Instead of allowing upstream failures to
    directly propagate to the application, SphinxGate can detect failures,
    control retries, use circuit breakers and rate limiting, and route to an
    appropriate alternative where possible."


7. DIFFERENCE BETWEEN FAILURE TYPES (CONCEPTUAL)
──────────────────────────────────────────────────────────────────────────────
    Failure              Meaning
    ─────────────────    ────────────────────────────────────────────────────
    Timeout              Provider didn't respond within allowed time
    429                  Too many requests / rate limit
    5xx                  Provider/server-side error
    Connection error     Can't establish communication
    Authentication error Credentials invalid
    Quota exhausted      Provider allocation/credits unavailable

    She doesn't need to memorize implementation details.
    She needs to understand: Not every failure should be treated the same way.


8. WHY RETRY ISN'T ENOUGH
──────────────────────────────────────────────────────────────────────────────
Mentor may ask: "If API fails, why don't you just retry?"

Answer:
    "Retry can help with transient failures, but repeatedly retrying an
    unhealthy provider can increase load and delay the application further.
    That's why the system combines bounded retries with mechanisms such as
    circuit breakers and fallback routing."


9. WHAT IS CASCADING FAILURE?
──────────────────────────────────────────────────────────────────────────────
    Provider becomes slow
            ↓
    Our application waits
            ↓
    More requests accumulate
            ↓
    More retries occur
            ↓
    Provider receives even more traffic
            ↓
    System becomes increasingly unstable

    This is the kind of problem SphinxGate is designed to contain.

14. WHY MULTIPLE SPHINXGATE INSTANCES?
──────────────────────────────────────────────────────────────────────────────
Because one gateway instance itself can fail.

    Bad:
        User → One SphinxGate server → Server crashes → Everything unavailable

    Better:
                  Load Balancer
                  /     |     \
                 /      |      \
              SG-1     SG-2    SG-3

    If one instance fails, traffic can potentially continue through others.


15. WHAT DOES A LOAD BALANCER DO?
──────────────────────────────────────────────────────────────────────────────
    A load balancer distributes incoming requests across available SphinxGate
    instances and can help avoid sending traffic to unhealthy instances.

19. WHY STATELESS?
──────────────────────────────────────────────────────────────────────────────

        Request 3 → Server C

    If critical state exists only inside Server A:
        Server A dies → State disappears → Scalability problem.

10. EXPLAIN RETRY TECHNICALLY
──────────────────────────────────────────────────────────────────────────────
    Request → Provider timeout → Is timeout retryable? YES
    → Retry → Failure → Backoff → Retry

    Why backoff?
    To avoid immediately hammering an already unhealthy provider.
    Current policy: bounded retries with exponential backoff.


11. EXPLAIN CIRCUIT BREAKER
──────────────────────────────────────────────────────────────────────────────
    CLOSED
     ↓ (repeated failures)
    OPEN
     ↓ (recovery period)
    HALF-OPEN
     ↓
    success → CLOSED
    failure → OPEN

    Why?
    To stop repeatedly sending requests to a provider that is already unhealthy.


12. EXPLAIN RATE LIMITING
──────────────────────────────────────────────────────────────────────────────
    Request → Rate limiter → within limit?
        YES → provider
        NO  → 429

    The gateway can reject excessive requests BEFORE making the upstream call.

25. LIKELY TECHNICAL QUESTIONS
──────────────────────────────────────────────────────────────────────────────
Q: "Why not put retry logic inside every provider adapter?"
A: "Because resilience is a cross-provider concern. Keeping it centralized
   prevents duplicated logic and ensures consistent policies across providers."

Q: "Why isn't the provider adapter responsible for the circuit breaker?"
A: "The adapter should understand how to communicate with its provider. The
   resilience engine should decide how to react when that communication fails.
   Keeping those responsibilities separate makes the architecture easier to
   extend."

Q: "What happens if the provider returns an invalid response?"
A: "The adapter or gateway should validate/normalize the response, and malformed
   or unsuccessful responses should be handled as failures rather than being
   presented as successful output."

Q: "What happens if all providers fail?"
A: "SphinxGate returns a structured failure. It doesn't fabricate a successful
   response."

Q: "Why not just use one provider?"
A: "A single provider creates a stronger dependency on that provider's
   availability, quota and performance. Multiple compatible providers provide an
   opportunity for resilience and continuity."

Q: "Why seven providers?"
A: "The goal isn't simply to maximize the provider count. We wanted to
   demonstrate that the generalized architecture works across different provider
   types: three LLM providers and four public APIs."


26. SUBTLE TECHNICAL QUESTION — DISTRIBUTED STATE
──────────────────────────────────────────────────────────────────────────────
Mentor: "If your circuit breaker is stored in memory and you run three
SphinxGate instances, will all instances know the provider is unhealthy?"

Answer:
    "Not necessarily. Local in-memory state would be instance-specific. For a
    horizontally scaled production deployment, shared or coordinated state would
    be needed for things such as distributed rate limiting and potentially
    provider health or circuit state, depending on the desired consistency model."


27. SUBTLE QUESTION — RESILIENCE AS BOTTLENECK
──────────────────────────────────────────────────────────────────────────────
Mentor: "What happens if your resilience mechanism itself becomes a bottleneck?"

Answer:
    "The resilience layer needs to remain lightweight and asynchronous.
    Components such as rate limiting and circuit state should have bounded
    memory and efficient access patterns. At larger scale, shared state and
    telemetry would need dedicated infrastructure rather than blocking the
    request path."

29. HER 1-MINUTE TECHNICAL PRESENTATION
──────────────────────────────────────────────────────────────────────────────
    "Technically, SphinxGate is built as a FastAPI-based gateway using Python
    and httpx for communication with upstream providers. The architecture
    separates the gateway, centralized resilience engine and provider adapters.

    The resilience engine provides timeout handling, failure classification,
    bounded retries with exponential backoff, circuit breakers, rate limiting and
    fallback routing. Provider-specific behavior is isolated through adapters,
    allowing us to support both LLM providers such as Gemini and Groq and public
    APIs such as Open-Meteo and Frankfurter without changing the core resilience
    logic.

    We currently have seven providers and 122 automated tests passing. We use
    mocked provider behavior for deterministic resilience testing and have also
    manually demonstrated circuit breaking, rate limiting and fallback.

    From the DevOps and security perspective, provider credentials remain
    server-side, Docker and CI/CD are part of the deployment approach, and secret
    scanning and secure runtime configuration are part of our security hardening.
    The phased architecture makes the remaining work feasible because each phase
    builds on an already working foundation."

3. EXAMPLE

    Gemini
    Error rate → 81%

The important thing: AI EXPLAINS EVIDENCE.

──────────────────────────────────────────────────────────────────────────────
RCA = Root Cause Analysis. Why did this incident happen?

Example:
    High latency → timeouts → retries → more failures → circuit opened

Copilot should help connect those events.

    - provider health
